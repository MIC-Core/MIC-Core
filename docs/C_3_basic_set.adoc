== Basic Set of Attributes

=== Introduction
Within the basic attribute set, a small number of attributes provide the most essential information required to support basic functionalities such as search, overview, analysis, and identification of reusable simulation tasks.

The following attributes represent the *essential elements of the minimal metadata set:*

*	*Simulation Task*

*	*Item under Test*

*	*Simulation Objective*

*	*Used Model*

*	*Used Tool*

Together, these attributes allow users to understand at a basic level:

*	what simulation was performed

*	what system or component was analyzed

*	what the purpose of the simulation was

*	which model was used

*	which tool was used to perform the simulation

Even this small set of attributes already enables several basic use cases, such as searching for simulations, identifying similar simulation tasks, or selecting candidate simulations for reuse.

The following illustrates how this information is linked to the development and simulation process.

=== Purpose 

Metadata for simulation tasks are currently only sparsely established in industrial environments. Different tools and organizations often use heterogeneous or proprietary metadata structures, which limits the ability to analyze, search, and reuse simulation information across projects and tools.

To lower the barrier for implementation, this specification defines a *minimal basic set of attributes* for simulation tasks. 

The goal of this basic set is *not to provide a comprehensive metadata model*, but to define a *minimal set of information that enables basic functionalities and use cases* such as analysis, search, overview, and reuse of simulation tasks.

It is important to note that *traceability requirements are always use-case specific.* Depending on the intended use case, different metadata attributes may be required. Therefore, the attribute set defined in this appendix does *not attempt to cover all possible traceability requirements.*

Instead, it defines a *small common baseline* that can support several basic use cases and that can easily be extended for more advanced or domain-specific scenarios.

Typical basic use cases include:

*	searching for existing simulation tasks
*	identifying simulations related to a specific product or project
*	obtaining an overview of performed simulations
*	identifying candidate simulations for reuse
*	performing simple evaluations of simulation activities

The basic set can serve as a *starting point for organizations introducing simulation metadata management* and may be extended with additional attributes depending on specific use cases.

=== Design Principles

The definition of the basic attribute set follows several key principles.

*Minimal effort for implementation*

Only attributes that provide clear value for traceability and reuse are included. The number of required attributes is intentionally kept small in order to simplify implementation.

*High user acceptance*

User acceptance is considered a critical success factor. Therefore, the attribute set avoids excessive manual data entry requirements and focuses on information that is typically already available.

*Tool-supported metadata generation*

Where possible, metadata should be automatically provided by simulation tools, simulation environments, or project management systems. This reduces manual effort and increases data consistency.

Typical sources for metadata include:

*	project management systems

*	simulation tools

*	model management environments

*	user-provided engineering information

=== Scope of the Basic Attribute Set

The basic attribute set focuses on metadata that support *basic functionalities such as search, overview, analysis, and reuse of simulation tasks.*

The attributes cover four main aspects:

*Administrative and project context*

Information that connects the simulation task to a project or request context.

Examples include:

*	ordering project

*	specific product

*	simulation task

*Simulation context*

Information describing the purpose and object of the simulation.

Examples include:

*	item under test

*	simulation objective

*	quality or evaluation criteria

*Used elements*

Information about the key elements used during the simulation.

Examples include:

*	simulation models

*	simulation tools

*	(relevant parameters or test cases)

The identification of specific relevant parameters is *use-case dependent* and may require user interaction or tool-specific support. Therefore, these elements are considered optional in the basic attribute set. 

*Results*

Information about the resultsof the simulation.

Examples include:

*	Task status

*	Credibility fulfilled

* objectives fulfilled

This information enables users to understand *what was simulated, why it was simulated, and with which tools and models the simulation was performed.*

=== Identification of Core Elements
For several key elements within the basic attribute set, it is recommended that the following information be available:

*	*Name*

*	*Identifier*

*	*Version*

This applies in particular to:

*	specific product

*	simulation task

*	item under test

*	used model

*	used tool

No specific format or implementation mechanism is defined by this specification. Organizations should use their *existing company-specific conventions, identifiers, and versioning schemes.*


=== Relation to Extended Metadata

The basic attribute set is intentionally limited to information required for basic use cases

More detailed metadata may be required for advanced use cases such as:

*	detailed reproducibility of simulations

*	credibility assessment of simulation results

*	automated simulation workflows

*	detailed analysis of simulation execution

Such information can be captured using *extended metadata sets* defined in this specification or in organization-specific extensions.

The basic set should therefore be considered as a *foundation layer* that can be extended without affecting interoperability.

=== Implementation Considerations

When implementing the basic attribute set, it is recommended that organizations prioritize:

*	*automatic generation of metadata by simulation tools*

*	*integration with project or simulation request management systems*

*	*minimal manual input by simulation engineers*

This approach helps ensure both *data quality and user acceptance,* which are essential for the successful adoption of simulation metadata management.

=== Structure of the Basic Attribute Set

The basic attribute set is structured into a small number of logical groups.

The following attribute groups are defined:

| Administrative Data | Basic identification and project context of the simulation task
| Analysis | Purpose and object of the simulation
| Used Elements | Key tools and models used in the simulation
| Result Status | High-level outcome of the simulation task | 
|===

This grouping supports common basic use cases such as *search, overview, analysis, and reuse of simulation tasks.*

=== Considerations for Parameters and Test Cases

Some information elements that are often important for deeper analysis or reproducibility of simulations are only included as optional in the basic attribute set.

*Used Parameters*

Information about *used simulation parameters* can be highly relevant for understanding and reproducing simulation results. However, the identification of the parameters that are truly relevant for a simulation task is typically *simulation-specific and use-case dependent.*

In many cases, determining the relevant parameters requires:

*	user interaction

*	engineering judgement

*	or dedicated tool support

Including parameters in a minimal attribute set would therefore introduce additional effort for the user and could negatively affect user acceptance. For this reason, *used parameters are only included as optional in the basic attribute set, although they may be recommended in the extended metadata sets.

=== Test Cases

Test cases are another important element for describing simulation activities. However, currently there are *no widely established cross-tool standards for the description and exchange of simulation test cases.*

Most simulation tools provide only *tool-specific and proprietary export formats* for test cases and related execution settings.

Because of this lack of standardized representations, *test cases are only included as optional in the basic attribute set. Organizations may include such information in extended metadata structures or tool-specific integrations.
 

=== Example TUse Cases

The defined attribute set enables several basic traceability use cases.

Examples include:

*Search for related simulations*

Example queries:

*	Simulations performed for a specific project

*	Simulations analyzing a specific item under test

*	Simulations executed with a specific tool version

*Reuse of simulation setups*

The attributes *used Model, used Tool, and simulation Objective* allow engineers to identify simulation tasks that may serve as templates for new simulations.

*Analysis of simulation activities*

Basic metadata allow organizations to analyze simulation activities, for example:

*	which tools are used in which contexts
*	which models are used for specific analyses
*	which simulations support specific products or projects


=== Automatic Metadata Generation
To ensure high user acceptance, the basic attribute set is designed so that a large portion of the metadata can be generated automatically.

Typical examples include:

[cols="1>m,2^e,7<",width="70%",align="center",frame="topbot",options="header"]
|===
| Attribute | Automatic Source
| Simulation Task ID| Simulation management system
| Used Tool | Simulation tool
| Used Tool Version | Simulation tool
| Used Models | Simulation tool
| Project Name | Project management system | 
|===


Only a small number of attributes, such as *simulation Objective or Item under Test*, typically require manual input by the simulation engineer or originate from the simulation request.
